# Libraries

A Hillnote **library** is a user-created 📚 folder inside `documents/` that holds long documents — textbooks, statutes, manuals, standards, long reports — imported as **volumes**. A volume is *not* one giant markdown file: it is a folder with **one editable markdown file per outline node** (a section) plus plain-text manifests, so a 300-page book becomes ~400 small sections with stable ids, page numbers and ready-to-paste citations. Agents never load a whole book; they search for sections and read the few that matter.

**Golden rule: library questions are `list_playbooks` → `get_library_map` → `search_library` → `get_library_section`; never `read_document` a whole book.** A matching playbook replaces the search (`read_playbook` returns its pinned sources). Cite with `citation.markdown`.

## Mode notes — read this first

- **Remote MCP:** the five read-only library tools (`list_libraries`, `get_library_map`, `get_library_outline`, `search_library`, `get_library_section`) plus the four playbook tools over the synced workspace, and over **cloud libraries** shared with the user (see below). Ranking is keyword-based (`engine: "csv-keywords"` / `"csv-keywords+grep"`); `mode: "semantic"`/`"hybrid"` fall back to keyword and report `semanticUnavailable`. Unscoped searches cover at most 30 volumes per call (`contentSearchPartial: true` + a `note` when capped) — scope with `library`/`volume`.
- **Local MCP:** the same nine tools with identical parameters and envelopes, plus `open_library` (App UI) to put a library's landing page or a section on the user's screen. Same keyword engine; body grep is bounded (≤ 20 files, 1.5 s) and reports `contentSearchPartial` when the budget cuts it short.
- **In-app Chat (Hillnote itself):** the same tools backed by the app's SQLite full-text index (`engine: "fts5"`, semantic/hybrid when the library has embeddings). The `_hint` there names `replace_document_content`; on MCP the editing tool is `replace_content`.
- **Files:** everything is `cat`/`rg`-able — see the CLI recipe below. Edit section bodies freely; **never hand-edit** `sections.csv`, `pages.csv`, `outline.md`, `library.json` or `volume.json` (they are regenerated by Reindex).

## What a library is on disk

```
documents/<Library>/
├── library.json              # marker + settings + volumes[] summary + stats   (never hand-edit)
├── <Library>.md              # the CARD — the only registered document: ## Summary (user text) + ## Contents (generated catalog)
└── <Volume Title>/           # one volume = one imported document (never registered, never in the sidebar)
    ├── volume.json           # source/ingest metadata (source.file = the original PDF/DOCX, pages, status)
    ├── outline.md            # generated nested outline: - [Title](sections/0003-….md) · pp. 12–15 · s-p0d3vx7k
    ├── sections.csv          # derived manifest: id,order,level,parent,title,file,pageStart,pageEnd,…,keywords
    ├── pages.csv             # page → section map + page-start prefixes (PDF sources)
    ├── figures.csv           # figure/page-image catalog with captions + OCR text (when extracted)
    ├── summaries.csv         # optional per-section AI summaries
    └── sections/
        ├── 0001-preface.md
        ├── 0002-chapter-1-….md
        └── 0287-pages-244-248.md
resources/pdfs/<Library>/<Volume Title>.pdf      # the original (≤ 100 MB); page citations point here
resources/images/<Library>/<volume-slug>/…       # extracted figures / page rasters
```

Every section file starts with frontmatter the tools rely on — keep it intact when editing:

```markdown
---
hillnote: library-section
library: lib-9f3a2c1e
volume: vol-7k2m0p4q
id: s-p0d3vx7k
title: 1.1 Atomic Structure
level: 2
parent: s-7h2kq9m1
order: 3
pages: [12, 15]
printedPages: ["4", "7"]
source: pdf
ocr: false
ingestHash: fnv1a-8c1e2a44
---

# 1.1 Atomic Structure

…body…
```

Ids: libraries `lib-…`, volumes `vol-…`, sections `s-` + 8 chars (unique per workspace, stable across edits, renames and moves), figures `f-p0013-01`. `pages` are 1-based PDF page ordinals; `printedPages` are the labels printed on the page.

## The read tools (same names, parameters and envelopes everywhere)

1. **`list_libraries(workspace, query?, limit?, offset?)`** → `{ workspace, libraries: [{ id, title, path, card, emoji, language, stats: { volumes, sections, words, figures }, volumes: [{ id, title, path, folder, sourceKind, pages, sections, words, figures, status, synced, updatedAt }], summary, status, updatedAt }], count, total, offset, hasMore, note?, _hint }`. Start here when the user mentions a book, manual, law text or long document they imported.
2. **`get_library_map(workspace, library?, volume?, depth?, maxChars?)`** — **read this first for any question about a library.** A compact map of what the library (or one volume) actually contains: every section with its page range and AI summary, capped to fit a prompt (`depth` 1–6, default 2 = chapters + their children; `maxChars` 200–20000, default 4000 — entries past the cap are counted and reported, never silently dropped). Omit `library` for every library in the workspace. Search ranks passages that *look like* the query; only the map shows the whole shape. Use it to pick what to read, to answer structural questions ("how does this build up to X", "where should I start"), and to tell "the library does not cover this" apart from "my search did not surface it" — the second is never evidence of the first.
3. **`get_library_outline(workspace, library, volume?, parent?, depth?, includeSummaries?, offset?, limit?)`** — without `volume`: the library plus every volume with its top-level chapters (`topLevel`, ≤ 12 each; the one-call orientation). With `volume`: the paginated outline tree — nodes `{ id, title, level, parent, order, pages, printedPages, words, childCount, figureCount, file, retired?, edited?, summary? }`, `depth` 0–6 (0 = all levels, default 2), `parent` = a node id to list its subtree, `limit` ≤ 300.
4. **`search_library(workspace, query, library?, volume?, mode?, kinds?, limit?, offset?, snippetChars?)`** → ranked `results: [{ library, volume, kind: "section"|"figure", section: { id, title, level, parent, pages, file }, figure?, score, snippet, citation: { label, section, page, pages, printedPages, markdown }, pendingUserReview? }]` plus `scope`, `count/total/offset/hasMore`, `engine`, `contentSearchPartial?`. Quote phrases (`"carbon dioxide"`); add `kinds: ["figure"]` to search figure captions/OCR text. Snippets mark hits with `**`.
5. **`get_library_section(workspace, section, library?, volume?, include?, maxChars?, offset?, inlinePageMarkers?)`** — `section` is an id, a section file path (a `doc:…#s-…` citation works too) or an exact/prefix/substring title (`library`/`volume` narrow it; other title matches come back as `alternatives`). Returns the body slice (`body`, `bodyRange: { offset, end, total }`, `hasMore` — loop with `offset = bodyRange.end`; `maxChars` default 6000, `0` = metadata only), `pageBreaks: [{ page, printed, offset, confidence }]`, `pageRange`, `pendingUserReview` (unresolved sync conflict markers — do not edit until the user resolves them), `citation`, and on request (`include`) `summary`, `children`, `neighbors: { prev, next, parent, firstChild }`, `figures`; `neighbors`/`children` also bring `ancestors`. `inlinePageMarkers: true` inserts `[p. N]` lines at page starts.

References are forgiving: `library` = id, folder path (`documents/<Library>`, with or without the prefix, the card or `library.json` path) or title; `volume` = id, folder name or title; unique substrings work. Errors list what exists ("Known libraries: …") — read them instead of guessing.

## Playbooks

A **playbook** is the user's own written answer to "when someone asks this kind of question, read these exact sources and answer this way". It belongs to one library and pins its sources as `doc:` links, so following one replaces searching.

- **`list_playbooks(workspace, library?, limit?)`** — titles + the one-line `when` trigger, no bodies. Cheap: call it early for anything that sounds routine or repeated. Following the user's playbook beats improvising.
- **`read_playbook(workspace, playbook, library?, resolve?, maxChars?)`** — the instructions **plus the full text of every pinned source** in one call (`resolve` default true; `maxChars` 24000 shared across all bodies). Follow the instructions, cite from those bodies, and fall back to `search_library` only for what they don't cover. If a pinned source is reported missing, say so rather than answering as though you had read it.
- **`create_playbook(workspace, library, title, when, instructions?, references?, tools?)`** — save a repeatable approach when the user asks. **Offer** to save one, and save it only once they agree, when the user states a standing preference ("always quote the statute", "from now on…"), corrects your approach in a way that generalises, asks a kind of question they have clearly asked before, or the answer needed a non-obvious set of sources that will be needed again. Don't offer for a one-off lookup, while the user is still exploring, or when an existing playbook nearly covers it — `list_playbooks` first and `update_playbook` instead. Keep `when` narrow and concrete (a vague trigger matches every later question); put the exact `citation.markdown` links you just used in `references`. Once it is saved, tell the user what it will now do. The app marks playbooks an assistant wrote.
- **`update_playbook(workspace, playbook, library?, title?, when?, instructions?, references?, tools?)`** — only the fields you pass change, so the user's hand edits survive; `references` and `tools` **replace** the whole list (send the full list). `title` changes the display name, not the filename. There is no delete tool — the user deletes playbooks in the app.

On disk a playbook is `documents/<Library>/playbooks/<slug>.md` — one ordinary markdown file, the only file in a library nothing regenerates:

```markdown
---
hillnote: library-playbook
library: lib-9f3a2c1e
id: pb-twox8mtr
title: Case summary
when: A user asks for a summary of a single case.
origin: assistant
references:
  - doc:documents/Case Law/Vol 1/sections/0042-smith-v-jones.md#s-p0d3vx7k
tools:
  - search_library
created: "2026-10-22T08:20:02.939Z"
updated: "2026-10-22T08:20:02.939Z"
---

1. Read the pinned judgment …
```

In Files mode, write that shape yourself (`hillnote`, `title` and `when` are the minimum; set `origin: assistant` on one you wrote). Playbooks don't appear in the sidebar or the registry, but they sync and travel with a shared library.

## Cloud libraries

A **cloud library** (id `cl-…`) is a library hosted on hillnote.com and shared with the user, read-only. On remote MCP, every read tool — `list_libraries`, map, outline, search, section, `list_playbooks`, `read_playbook` — takes `library = <cl-id or title>` and `workspace` may be omitted to work only with shared cloud libraries. Playbook writes are refused on them (the owner edits the original). On local MCP, a cloud library the user has connected in the app shows up in `list_libraries`; queries against it go through the running app, so they fail with a clear message when Hillnote is closed — ask the user to open it.

## Citing

- `citation.markdown` → `[[<Volume> › <Section title>|doc:documents/<Library>/<Volume>/sections/<file>.md#<s-id>]]` — paste it into notes; Hillnote resolves it by the stable id even after the library is renamed or reindexed.
- `citation.page` → `doc:resources/pdfs/<Library>/<Volume>.pdf#p<N>` — opens the original page in the app's Files panel (PDF sources only; `null` otherwise).
- In prose, name the volume and pages: *Organic Chemistry 3e, §1.1 Atomic Structure (pp. 12–15)* — `citation.label` and `citation.pages`/`printedPages` carry exactly that.

## Editing a section

Sections are ordinary markdown documents: `replace_content` (or `insert_content`/`delete_content`) with `documentId = section.file` from `get_library_section` — the resolver accepts section paths and `doc:…#s-…` citations even though sections are not in the registry. Keep the frontmatter block; edit the body. Skip sections with `pendingUserReview: true`. The app re-indexes the file on save and regenerates `sections.csv`/`outline.md` itself — never edit those, `library.json` or `volume.json` by hand, and never create section files yourself (import documents through the library's landing page in Hillnote).

## Files mode / CLI recipe (Claude Code on the workspace folder)

```bash
cat "documents/<Library>/<Library>.md"                 # the card: summary + catalog of volumes with links to top-level sections
cat "documents/<Library>/<Volume>/outline.md"          # nested outline: title · pages · section id per line
rg -il "<term>" "documents/<Library>/<Volume>/sections/"   # which sections mention the term
cat "documents/<Library>/<Volume>/sections/0042-….md"      # read one section (frontmatter first)
```

`sections.csv` is the manifest (`id,order,level,parent,title,file,pageStart,pageEnd,…,keywords`) if you need page ranges or the keyword column; `pages.csv` maps pages to sections. Cite with `[[<Volume> › <Title>|doc:documents/<Library>/<Volume>/sections/<file>.md#<s-id>]]` and `doc:<source.file>#p<N>`.

## Gotchas

- `list_libraries` and the outline read only manifests (fast, no bodies). `search_library` on the MCP servers ranks titles + extracted keywords first and greps a bounded set of bodies — for a rare term that only appears mid-body, quote it and scope to a volume; the app's own search is full-text.
- A `note` on a volume ("still importing", "no sections.csv yet") means the import is unfinished or the workspace has not been pushed — say so rather than reporting an empty book.
- Encrypted section files come back with `encrypted: true` and an empty body; they are never indexed or searchable.
- Volume `synced: false` means the original is too large to sync and lives only on the importing machine — `citation.page` still points at its expected path; on another machine the user may need "Locate original…" on the landing page.
- Small local models see trimmed envelopes (no `section.file`/`citation.markdown` in search hits, shorter snippets); the ids are still there — `get_library_section(section = id)` fills the rest in.
